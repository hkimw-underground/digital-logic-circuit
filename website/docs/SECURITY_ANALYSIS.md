# 보안 분석

## 보안 모델
도어락은 두 조건이 모두 통과될 때만 열린다.

```text
출입 허용 = (정상 NFC 또는 정상 PIN) AND (YOLO 검사 통과 AND 등록 얼굴 일치)
```

기본 결과는 거부다. 카메라, 모델 파일, 필요한 라이브러리, 등록된 얼굴 정보 중 하나라도 없으면 문은 잠긴 상태를 유지한다.

## 위협 모델
| 위협 | 공격 방식 | 현재 대응 | 남은 위험 |
| --- | --- | --- | --- |
| 인증 수단 탈취 | NFC 카드 도난 또는 PIN 노출 | 1차 인증 후 카메라 검증을 요구한다. PIN은 bcrypt로 저장한다. | 등록 사용자가 실제로 있으면 문은 열릴 수 있다. |
| 기존 평문 PIN | 이전 등록 경로가 PIN을 평문 저장 | 모든 등록 경로가 `Database.add_user`를 사용한다. 일치한 기존 PIN은 bcrypt로 승격한다. | 오래된 DB 사본에는 평문 PIN이 남아 있을 수 있다. 배포 전 데모 PIN을 교체한다. |
| 화면 재생 공격 | 사진 또는 영상 재생 | YOLO nano가 얼굴 영역을 찾고, 휴대폰이나 화면을 차단하며, 얼굴 대조 전 눈깜빡임을 요구한다. | 정교한 영상 재생 공격에는 추가 확인 동작이 필요하다. |
| 영상 처리 실패 | YOLO 모델, OpenCV, `face_recognition`, `ultralytics`, 카메라 누락 | 준비되지 않으면 문을 열지 않는다. 데모 우회는 `DOORLOCK_VISION_MOCK=1`에서만 동작한다. | 설치 전 환경변수와 모델 경로를 확인해야 한다. |
| 무차별 대입 | PIN/NFC 반복 시도 | 실패 후 대기, 최종 판정 기준 3회 연속 실패 시 웹 화면 경고, 1시간 내 기준치 이상 실패 시 입력 무시 | 긴 시간 동안 나눠서 반복하는 시도에는 더 강한 정책이 필요하다. |
| 민감 정보 노출 | 실패 PIN/NFC 값이 로그나 알림에 남음 | PIN은 마스킹하고 NFC는 끝 일부만 남긴다. Discord mention은 비활성화한다. | 별도 로그 수집기가 원본 시리얼 스트림을 저장하지 않도록 해야 한다. |
| SQLite 쓰기 충돌 | 웹 화면과 서버의 동시 읽기/쓰기 | WAL 모드, `busy_timeout`, 공용 `Database` 함수, 읽기/쓰기 잠금 적용, SQLite backup API 사용 | 쓰기량이 많아지면 SQLite 한계에 도달할 수 있다. |
| 시리얼 신호 훔쳐보기/주입 | USB 또는 릴레이 배선 물리 접근 | 하우징 설치를 전제로 하고, 서버 명령은 `OPEN_DOOR`로 통일했다. | 프로토콜은 아직 평문이다. 더 높은 보안에는 응답 확인 방식이 필요하다. |
| 릴레이 우회 | 릴레이 또는 전원선 단락 | 하우징과 분리 전원 사용을 설치 기준으로 둔다. | 강제 개봉 감지 스위치는 아직 없다. |

## 운영 설정
| 변수 | 운영 값 |
| --- | --- |
| `DOORLOCK_VISION_MOCK` | 설정하지 않거나 `0` |
| `DOORLOCK_ALLOW_UNENROLLED_FACE` | 설정하지 않거나 `0` |
| `DOORLOCK_ALLOW_LEGACY_FACE_PICKLE` | 설정하지 않거나 `0` |
| `DOORLOCK_YOLO_MODEL_PATH` | 로컬 디스크의 학습된 nano 모델 파일 |
| `DOORLOCK_DB_PATH` | 공개 폴더 밖의 관리되는 경로 |
| `DOORLOCK_WEB_HOST` | 외부 접속이 필요 없으면 `127.0.0.1` |
| `DOORLOCK_DISCORD_WEBHOOK_URL` | 원격 알림이 필요할 때만 설정 |

## 다음 개선
1. 릴레이 명령 전에 시리얼 응답 확인 절차를 추가한다.
2. 눈깜빡임 횟수 또는 고개 회전 같은 무작위 확인 동작을 추가한다.
3. 강제 개봉 감지 스위치와 안전한 릴레이 차단 정책을 추가한다.
4. 백업 생성뿐 아니라 복구 테스트까지 수행한다.
